# Firefox startup page-creation race

Actual prior Windows CI run 38002188290, commit d563c82875b3ca820cfa5bd798fcd40ba878763e, failed `firefox_page_closure` during `open` -> its first `new_page`, before the closure scenario. The original log is copied as `windows-original.log`.

Bundled Firefox 157.0.1 remote source was extracted read-only from `/workspace/.rustwright-env/firefox/omni.ja` using unzip; Mozilla license headers are retained. `browsingContext-root.sys.mjs` lines751–762 create a visibility waiter on the previously selected browsing context before addTab, then lines814–819 await that waiter alongside initial new-document navigation. `BrowsingContextUtils.sys.mjs` lines278–296 wait up to100ms for WindowGlobal and throw the exact observed `DiscardedBrowsingContextError` message if unavailable. Foreground creation may therefore fail after allocating a tab because the previously captured context was replaced. `activate` lines355–365 also waits previous visibility, but fetches the selected browsing context when that subsequent command executes.

The driver now allocates in the background, receives the new context identifier, then activates that explicit context. The Creation guard remains live through activation and transfers only after success. Normal returned pages are still activated. There is no retry, no test delay increase, and no protocol error suppression. This changes the concrete capture-before-addTab boundary; unrelated concurrent context discard during later activation can still fail and trigger allocated-context retirement.

Five new controlled regressions require CI execution: three in `creation_visibility_tests.rs` model replacement during allocation and check successful single allocation, explicit activation, isolated owner preservation and exact cleanup; two in `creation_tests.rs` hold/reject activation and verify cancellation/error retirement before helper registration. Existing eight fake remotes gained explicit activate support, with subscription counters and gates preserved. The existing native `http_network_idle_parity::firefox_page_closure` case now performs five independently launched process/profile cycles, with visible-document, active-fetch, closure and waiter checks each time. Every cycle must pass; the first failure aborts, with no retry. Chrome remains one cycle and selected test counts stay unchanged. Headed/actionability scenarios must also pass.

Local rustfmt and whitespace checks passed. Compilation and browser tests were deliberately not run because the inherited environment had exhausted process resources; no new success count is claimed. Next CI should run `cargo test --workspace --lib --locked`, strict Clippy/MSRV checks, and the portable Chrome/Firefox suite including `http_network_idle_parity`, in headed Linux as well as headless Windows/macOS/Linux.

`before/`, `after/`, `source.sha256`, `report.json` and the extracted Mozilla source hashes preserve provenance. Prior frozen evidence remains untouched.

Diagnostic limit: the original native error has no stack/event trace identifying which visibility waiter failed. Bundled-source analysis supports the predecessor-context correction; controlled tests demonstrate that mechanism rather than reproducing native startup timing. Explicit activation selects the returned tab, but Firefox activate lacks foreground-create’s final new-document visibility wait. The new visible-state assertion and existing headed/actionability suites must validate the returned page; identical visibility timing at every stage is not claimed.
